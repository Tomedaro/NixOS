# Task-initiation contract candidates

Snapshot date: 2026-07-23.

This document describes the revised Milestone 1 contract candidate set. The Python module `python/ai_system/task_initiation_contracts.py` is authoritative for exact machine constraints (fields, types, validation, and reducer rules). Five stable boundary contracts are candidates for freezing; one provisional Receipt and one deferred Outcome are documented but excluded from the frozen set.

## Overview

Five stable boundary contracts cover the external message surfaces for the laptop-first task-initiation loop. One private aggregate owns internal lifecycle, state, and correlation without a `schema_version`. The loop begins when a user who already knows their task presses "Stuck" in Tasker. Ordinary software owns the entire lifecycle from ingress through observation; the model is a bounded proposal worker, not the controller.

No service, database, directory, or card projection is created in this milestone. The validators are pure, executable, and dependency-free.

## Stable candidates

| Schema | Boundary | Owner | Role |
| --- | --- | --- | --- |
| `task_initiation_stuck.v1` | Tasker → kernel | `task_initiation_contracts` | Untrusted "Stuck" ingress event. |
| `task_initiation_card.v1` | kernel → Tasker | `task_initiation_contracts` | Immutable display card with fixed controls and kernel-generated expiry. |
| `task_initiation_response.v1` | Tasker → kernel | `task_initiation_contracts` | User button action evidence. |
| `task_initiation_context.v1` | local builder | `task_initiation_contracts` | Local disclosure/audit manifest; not the exact API request. |
| `task_initiation_proposal.v1` | model → kernel | `task_initiation_contracts` | Semantic-only blocker + tiny-start output; no envelope metadata. |

## Provisional

`task_initiation_card_receipt.v1` is documented but **excluded from `ALL_SCHEMA_VERSIONS`**. It represents Tasker notification-posted evidence (`receipt_id`, `card_id`, `posted_at_epoch`). Milestone 3 must live-test whether Tasker can reliably report notification posting, offline replay, ordering, and clock behavior before freezing the exact field names or semantics.

A Receipt may arrive before or after Response. Same-ID replay is idempotent; conflicting reuse is refused; a late Receipt is evidence only.

## Deferred

`task_initiation_outcome.v1` is deferred to Milestone 5. No Outcome validator, projection path, or metric derivation exists in Milestone 1. The evidence Milestone 5 will need is documented below but its JSON shape is not frozen.

## Removed

The following schema identities from the previous 13-schema candidate are removed and have no `schema_version`, public validator, or registry entry:

- `task_initiation_task_ref.v1` — TaskRef is now an inline value object inside Stuck.
- `task_initiation_error.v1` — Error codes are private reducer values.
- `task_initiation_idempotency_record.v1` — Idempotency is a private canonical-hash reservation.
- `task_initiation_interaction.v1` — Interaction is the private unversioned aggregate.
- `task_initiation_run.v1` — Individual revisions are private records inside the aggregate.
- `task_initiation_queue_record.v1` — Queue policy is deferred to Milestones 2–3.
- `task_initiation_outcome.v1` — Deferred to Milestone 5.
- `task_initiation_transition_event.v1` — Transition evidence reuses `event.v1` normalization.

## Field-level contracts

### `task_initiation_stuck.v1`

```text
schema_version: literal "task_initiation_stuck.v1"
event_id: lowercase UUIDv4 (opaque to kernel; generated by Tasker)
source: literal "tasker"
occurred_at_epoch: positive integer, client event time subject to server clock-skew policy
task_ref: null | {
  source: literal "tasknotes",
  ref: normalized relative path matching Tasks/<relative>.md, <= 500 chars,
  no absolute path, backslash, NUL, ".", or ".." segment
}
task_description: null | normalized non-empty text, <= 500 chars
```

At least one of explicit TaskRef, an exact active session, or description must resolve later; Stuck itself may omit both fields because the active session is a valid resolver input. If both TaskRef and description are present, TaskRef keeps precedence.

No client-supplied `idempotency_key`, `expires_at_epoch`, or `privacy_class`. `(message kind, event_id)` is the idempotency identity; the private reservation stores the canonical payload hash. The kernel validates future skew, records `received_at_epoch`, computes authoritative Stuck expiry as `occurred_at_epoch + configured_stuck_ttl_seconds` (default 7200), and rejects when `received_at_epoch >= computed expiry`.

### `task_initiation_card.v1`

```text
schema_version: literal "task_initiation_card.v1"
card_id: kernel-generated lowercase UUIDv4; opaque to Tasker
interaction_id: kernel-generated lowercase UUIDv4; opaque to Tasker
revision: positive integer
issued_at_epoch: positive integer generated by kernel
expires_at_epoch: positive integer generated by kernel; > issued_at_epoch
title: normalized text, 1..120 chars
task_label: normalized text, 1..500 chars
blocker: {
  category: one of BLOCKER_CATEGORIES,
  summary: normalized text, 1..300 chars
}
tiny_start: {
  kind: "physical" | "digital",
  instruction: normalized text, 1..300 chars,
  estimated_minutes: positive integer,
  completion_signal: normalized text, 1..200 chars
}
start_countdown_seconds: positive integer generated by kernel; trial cap is runtime policy
actions: exact ordered list [
  {id: "start", label: "Start"},
  {id: "shrink", label: "Shrink"},
  {id: "blocked", label: "Blocked"},
  {id: "defer", label: "Defer"}
]
dismiss_action: literal "dismiss"
```

The Card is immutable. It carries no `run_id`, `proposal_id`, `task_fingerprint`, mutable `status`, `shown_at_epoch`, `responded_at_epoch`, `execution_policy`, or `privacy_class`. The kernel stores correlations privately. `expires_at_epoch` is authoritative because the kernel produced it.

Selecting Start authorizes Tasker to start one local ephemeral countdown for exactly `start_countdown_seconds` while it enqueues the Response. The initial cap is 600 seconds, enforced by the private Card policy gate rather than by schema identity. Countdown failure does not cancel or rewrite the Start Response. The countdown has no authority to write TaskNotes, emit `action.v1`, alter repository session state, invoke recovery targets/capabilities, launch an application or URI, or persist a durable commitment.

### `task_initiation_response.v1`

```text
schema_version: literal "task_initiation_response.v1"
response_id: lowercase UUIDv4
card_id: opaque lowercase UUIDv4 copied from Card
action: "start" | "shrink" | "blocked" | "defer" | "dismiss"
detail: null | normalized text <= 500 chars; permitted only for shrink/blocked
occurred_at_epoch: positive integer, client button time subject to server clock-skew policy
```

No `idempotency_key`, `interaction_id`, `run_id`, `card_revision`, `task_fingerprint`, client `expires_at_epoch`, or `privacy_class`. The kernel looks up every authoritative value by `card_id`. First-response-wins. Server receipt-time expiry is authoritative.

A valid Response arriving before any Card Receipt is accepted. It proves the Card reached an actionable surface. A later valid Receipt adds posting evidence only; it cannot reopen, invalidate, or change the accepted action.

### `task_initiation_context.v1`

This contract is the local disclosure/audit manifest, not the exact provider request:

```text
schema_version: literal "task_initiation_context.v1"
context_id: local lowercase UUIDv4
interaction_id: local lowercase UUIDv4
revision: positive integer
task_fingerprint: lowercase SHA-256
policy_version: literal policy identifier
generated_at_epoch: positive integer generated locally
expires_at_epoch: positive integer generated locally; > generated_at_epoch
privacy_class: literal "sensitive_personal"
disclosed_facts: {
  task: {label: normalized text <= 500},
  followup: null | {
    action: "shrink" | "blocked",
    detail: null | normalized text <= 500,
    prior_tiny_start: normalized text <= 300
  },
  project_summary: null | {title: text <= 200, summary: text <= 1000},
  session_capsule: null | {summary: text <= 1000, ended_at_epoch: positive integer},
  recent_interactions: bounded list of {
    user_action: null | "start" | "shrink" | "blocked" | "defer" | "dismiss",
    terminal_status: "completed" | "expired" | "superseded" | "refused" | "failed",
    resolution_reason: normalized text <= 120,
    occurred_at_epoch: positive integer
  },
  helper_material: bounded list of {label: text <= 200, excerpt: text <= configured bound}
}
provenance: bounded list of {
  category: one of PROVENANCE_CATEGORIES,
  source_ref_sha256: lowercase SHA-256,
  observed_at_epoch: positive integer,
  fresh_until_epoch: positive integer >= observed_at_epoch
}
omissions: de-duplicated sorted list of current OMISSION_CODES
model_content_sha256: lowercase SHA-256 of the canonical minimal model-content payload
```

No echoed `limits` or `may_mutate_tasknotes`. The builder enforces bounds from local runtime policy and has no mutation capability.

`api_payload_from_context(manifest, policy=...)` reconstructs and validates the nested allowlisted facts before returning only the non-null semantic keys from `disclosed_facts`: `task`, `followup`, `project_summary`, `session_capsule`, `recent_interactions`, `helper_material`. It is safe to call with an unvalidated manifest: unknown nested fields are rejected rather than copied. It never returns IDs, task fingerprint, policy version, provenance, omissions, privacy class, source paths, or absolute/tilde/file-URI paths. `model_content_sha256` is the canonical SHA-256 of this minimal payload alone.

### `task_initiation_proposal.v1`

```text
schema_version: literal "task_initiation_proposal.v1"
blocker: {
  category: one of BLOCKER_CATEGORIES,
  summary: normalized text, 1..300 chars
}
tiny_start: {
  kind: "physical" | "digital",
  instruction: normalized text, 1..300 chars,
  estimated_minutes: positive integer,
  completion_signal: normalized text, 1..200 chars
}
```

The model/deterministic worker emits semantic content only. No proposal/context/interaction/run IDs, task fingerprint, source, status, timestamps, expiry, execution policy, latest error, privacy class, or `content` envelope. The private kernel record attaches identity and timestamps.

The deterministic proposal gate applies `contains_direct_execution` from `obsidian_contracts` with the union of `DIRECT_EXECUTION_FIELDS` and task-initiation-specific keys (`action`, `raw_action`, `action_file`, `path`). A separate private proposal policy gate applies the initial `estimated_minutes <= 10` safety ceiling; the public schema only requires a positive integer.

## Task resolution

Same precedence as before: explicit TaskRef → active session (`status == "active"`) → description → refuse. An invalid/missing explicit reference never falls through. The resolved task is fingerprinted as lowercase SHA-256 of canonical UTF-8 data with NUL separators.

The fingerprint is recomputed when recording Context, before Card publication, and before Response acceptance. A mismatch atomically supersedes the interaction (`task_changed`).

## Private aggregate and lifecycle

One private aggregate (`InteractionAggregate`) owns all internal state without a `schema_version`. Delivery, Receipt, Response, and evidence issues are stored on the matching private revision so evidence from an older Card cannot classify a newer Card. The module exposes the following pure helpers:

| Function | Purpose |
| --- | --- |
| `_new_interaction(stuck, *, received_at_epoch, policy)` | Create fresh aggregate; compute server TTL; reserve the Stuck identity/payload. |
| `_attach_resolved_task(state, resolved_task, *, now_epoch)` | Attach the canonical task and initial fingerprint. |
| `_verify_task_at_gate(state, resolved_task, *, gate, now_epoch)` | Recompute the fingerprint before context, Card, or Response; supersede on mismatch. |
| `_record_context_prepared(state, context, resolved_task, *, now_epoch, policy)` | Verify phase/deadline/task identity, enforce the runtime disclosure policy, and bind one validated local manifest for the next revision. |
| `_record_proposal_validated(state, proposal, *, now_epoch, policy)` | Require a live prepared Context, validate semantic Proposal plus runtime policy, and bind it to the same next revision. |
| `_record_card_published(state, card, *, now_epoch, resolved_task, policy)` | Require the prepared Context and Proposal, enforce phase/deadline/interaction/revision/uniqueness/task/semantic binding, and publish one non-expired immutable Card. |
| `_record_card_receipt(state, receipt, *, received_at_epoch)` | Record revision-local provisional Receipt evidence with replay/conflict checks. |
| `_record_delivery_result(state, *, card_id, result, occurred_at_epoch)` | Record revision-local adapter delivery evidence. |
| `_apply_response(state, response, *, received_at_epoch, resolved_task, policy)` | Recheck task identity, enforce server expiry and first-response-wins, and support exact replay. |
| `_advance_time(state, *, now_epoch, policy)` | Drive pre-Card request expiry, current-Card expiry, and Start observation deadlines. |

### Ordering and lifecycle rules

1. Validate/deduplicate Stuck, compute server expiry, resolve the task, and attach its fingerprint. Same-ID/same-payload replay is a no-op; same-ID/different-payload reuse is an idempotency conflict.
2. Reducer operations are phase- and deadline-guarded. Initial task attachment is allowed only before preparation; Context and Proposal can be prepared only in `preparing`; and Card publication requires both artifacts for the same exact next revision. Pre-Card work is refused after the Stuck deadline, and a Card cannot be published at/after its own expiry.
3. Recheck the task fingerprint before Context preparation and Card publication. The Context's task label must match the resolved task. Build and hash the exact minimal API payload (`model_content_sha256`), validate and bind the semantic Proposal, then require the Card's task label, blocker, and tiny-start content to match those kernel-owned inputs. Card publication moves `preparing → awaiting_response`; Receipt is not a prerequisite.
4. Receipt may add revision-local `card_posted_at_epoch` in any nonterminal or terminal phase. Exact replay is a no-op, conflicting same-ID reuse is refused, and evidence from one revision never alters another. A timely valid Receipt is stronger than an earlier `confirmed_not_posted`/`ambiguous` attempt result for a nonterminal Card: posting evidence is retained and prevents later classification as not posted. Receipt never changes the accepted action or reopens a terminal aggregate.
5. Recheck the task fingerprint before Response acceptance. A valid first Response received before authoritative Card expiry is accepted even with no Receipt. Exact replay returns the prior state without incrementing `state_version`; conflicting same-ID reuse is refused; a distinct later Response is `card_already_responded`. Aggregate `first_response_*` values retain the earliest accepted response across revisions; Start times are tracked separately. Client timestamps are populated only when issuance/expiry/skew ordering is valid; otherwise the action remains accepted and revision-local `response_timestamp_inconsistent` is recorded.
6. `_record_delivery_result` records first-wins adapter evidence on the identified revision only. Exact duplicate evidence is a no-op; contradictory replacement is refused. Late evidence for an older Card cannot affect the current Card. After any Response it is retained diagnostically and cannot invalidate the action.
7. `shrink` or `blocked` completes the current private Revision and returns to `preparing`; a fresh Context and Proposal are required before publishing the next Card. At the configured revision ceiling (default 3), terminalize `completed/shrink_limit_reached` or `completed/blocked_unresolved`. `defer` and `dismiss` terminalize `completed/deferred` and `completed/dismissed`.
8. `start` records user action, authorizes the already-authorized Tasker countdown, and moves to `observing` with a private deadline. It emits no action command. At the deadline, terminalize `completed/start_observation_elapsed`. Preparation functions cannot reopen an observing or terminal interaction.
9. Card expiry with no Response reads only the current revision's `delivery_evidence`: `confirmed_not_posted → expired/card_not_posted_before_expiry`, `ambiguous → failed/delivery_ambiguous`, `posted|none → expired/card_expired_without_response`.
10. The original Stuck TTL governs only pre-Card work. After Card publication, Card expiry governs response waiting; after accepted Start, the observation deadline governs completion. Terminal state is immutable.

`user_action`, `terminal_status`, and `resolution_reason` are stored separately; there is no combined `user_disposition` enum.

## Intended Outcome evidence (Milestone 5)

Documented but not frozen:

- **user evidence**: each accepted `user_action`, detail, and occurrence time;
- **system evidence**: `terminal_status` and `resolution_reason` as separate dimensions;
- **delivery evidence**: request occurrence/receipt, Card issue, Card posting when proven, retries, expiry, supersession, and ambiguity;
- **observation evidence**: micro-action completion, ten-minute engagement, and observation deadline;
- **feedback evidence**: made starting easier, wrong task, privacy correction, and annoyance/dismissal signal.

Four independent latency formulas (return unknown when a required timestamp is absent or ordering is contradictory):

```text
request_to_card_posted = card_posted_at - request_occurred_at
card_posted_to_first_response = first_response_at - card_posted_at
card_posted_to_start = start_at - card_posted_at
total_request_to_start = start_at - request_occurred_at
```

Primary initiation effectiveness is `card_posted_to_start` (initial trial threshold: <= 600 seconds). A Response without Receipt proves actionability but does not provide `card_posted_at`, so posting-anchored metrics remain unknown.

## Authority boundaries

| Actor | Authority |
| --- | --- |
| **Tasker** | Produces untrusted `stuck` and `response` requests. May report notification posting (provisional). Owns its device-local countdown and delivery metadata. |
| **Laptop kernel** (future) | Owns validation, resolution, private aggregate, expiry, deduplication, supersession, code-generated card controls, and observation deadline. |
| **Context builder** (future) | Reads only allowlisted sources. Produces `task_initiation_context.v1` manifest and minimal `disclosed_facts` payload. Has no mutation authority. |
| **Model** | Emits `task_initiation_proposal.v1` with semantic content only. Must not choose controls, authority, identity, task, or target. Output passes deterministic safety gate. |
| **Card** | Permits display and bounded response capture only. Start countdown is local, bounded, and non-consequential. |

Automatic authority remains limited to allowlisted reads, temporary run state, and response/observation evidence. Durable commitments, notes, TaskNotes, calendar, messages, and consequential external actions remain approval-gated.

## Reuse and consolidation

Reused:
- `obsidian_contracts.DIRECT_EXECUTION_FIELDS` and `contains_direct_execution` for recursive semantic safety checks.
- `context_schema.provider_result` and `context_hub_snapshot` as local builder inputs.
- `events.normalize_event` for future `event.v1` transition evidence.

Not reused:
- `action.v1`: carries execution authority; Start/Countdown never enters `AI/inbox/actions`.
- `phone_interaction.v1` or `phone_interaction_state.v1`: different lifecycle semantics.
- `queue.py`: manages stable vault JSON files, not Tasker device delivery.
- `agent_context.v1`: broader than the API disclosure allowlist.
- Recovery proposal/intervention/outcome schemas: different identity and semantics.

## Clock synchronization

Tasker and laptop clocks are expected to remain synchronized within the configured skew allowance (currently 300 seconds by default, but overrideable runtime policy rather than schema identity). Unreliable device clocks are a known risk; live validation is deferred to Milestone 3.
